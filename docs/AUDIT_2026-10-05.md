## 1. Summary for the owner

The code is carefully built where it matters most. Every multi-step write is one transaction, re-checks game state inside the write, and answers 409 when it loses a race. Every state-changing route checks the request origin and then the caller's permission before touching data. A scripted sweep of eight players' dashboards plus a spectator, on an open Night, found no other player's role. There is no P1 finding. The six P2 findings are about information players should not get, promises the app makes and does not keep, and one way to slow the server down without signing in.

What needs attention:

1. **Everyone sees "Waiting for the Hunter" before the moderator publishes (D26).** When a calculated result eliminates the Hunter, every player's screen switches to "Waiting for the Hunter" with a countdown. After a Night this tells the whole village that the wolves' victim was the Hunter and the Bodyguard did not stop it, hours before the result is public, and a moderator override can later contradict what they saw. Your call whether this beat is intended.
2. **A Mayor's double vote can give the Mayor away (D27).** The guide says the published ballot lists a Mayor's vote once "like everyone else's". When the Mayor's second vote flips a strict public leader, the published numbers cannot be explained any other way, and the only voter for the person eliminated is the Mayor.
3. **Three promises about privacy and backups do not hold (D23, D24, D25).** The guide tells players moderators cannot see who sent feedback, but a backup export links each feedback to a seat. The console says Reset and Restore preserve a backup, but spectators' Afterlife chat is deleted and was never in it. "Messages expire after N days" does not happen by itself, and every backup keeps private chat forever.
4. **One sign-in request can freeze a server instance (D22).** A crafted email in the seat sign-in form takes over a second of processor time at 32,000 characters and grows quadratically, before any rate limit applies. No account is needed.
5. **Lower priority:** 42 P3 items, including an unchanged "nothing new" poll doing as much database work as a full one (E11), sign-in timing that reveals which emails have accounts (D28), weak six-digit PINs allowed (D30), migration and setup scripts that never say which database they touched (D45), game-rule gaps in extreme settings (D39, D40, D41), and dead columns in the schema (R12).

Verified reassurances only: no finding exposes one player's role or a per-player private result (Seer inspection, for example) to another player. D26 and D27 leak indirect facts, not a named player's role.

## 4. Defects

Priority: **P1** exposes private data or opens a security hole; loses or corrupts data; leaves a core flow stuck with no way out; or tells users something false about their privacy or safety. **P2** wrong behavior or wrong user-visible text in a working flow; an operational gap that would hurt a real session; a doc that would lead an operator into a harmful step. **P3** hardening, cleanup, and wording that won't mislead anyone into harm.

### D22 · P2 · One unauthenticated sign-in request can freeze a server instance

**What happens.** `POST /api/seats/login` tests the identifier against an email pattern before the rate limiter runs. The pattern backtracks quadratically on a long string of dots. Anyone can send one request and tie up a Vercel function instance; during a live phase that stalls players and the moderator on that instance. Availability only; no data is exposed.

**Where.** `lib/roster/email-address.ts:4-5` (pattern); `app/api/seats/login/route.ts:39` (pattern runs) before `:41` (`enforceRateLimit`). The same pattern runs in `lib/auth/moderators.ts:77` (recovery), where the limiter keys only the first 80 characters of the email (`app/api/moderators/recover/route.ts:14`), so varying those characters avoids it. Nothing bounds the body or the identifier length earlier (`proxy.ts`, `next.config.ts`, `vercel.json`).

**Reproduction.** In a Vitest file, call the `POST` handler of `app/api/seats/login/route.ts` with a same-origin request and body `{"identifier":"a@" + ".".repeat(N) + ",","pin":"123456"}`. Time it. Observed at `d4aff81`: N=16,000 about 0.33 s, N=32,000 about 1.06 s, status 401. The bare pattern alone: 8k 66 ms, 16k 263 ms, 32k 1,033 ms, 64k 4,176 ms. A permanent test asserts that N=32,000 finishes in under 50 ms and that identifiers over 254 characters are refused.

**Fix.** Reject identifiers longer than 254 characters before any pattern (`lib/game/signups.ts:68` already does), in `seats/login` and `redeemModeratorRecoveryCode`; also make the pattern linear.

**Confidence.** Confirmed (reviewer and verifier).

### D23 · P2 · The guide says moderators cannot see who sent feedback, but a backup links every feedback to a seat

**What happens.** A player sends feedback; the guide promises moderators see "whether feedback came from a player, but not who sent it". Any moderator can download a backup and join the feedback row to its event to get the sender's seat. The moderator half of the same page says "the audit log and backups record who sent each one", which is slightly off too: the console's own event list strips the details, so only a downloaded backup or the database holds the sender.

**Where.** `app/guide/page.tsx:193` vs `:264`. `app/api/games/[gameId]/feedback/route.ts:71` stores `respondentId`; `lib/backup/snapshot.ts:96-97` exports `SELECT *` of `operational_events` and `pilot_feedback`; `app/api/games/[gameId]/export/route.ts:16` lets any game moderator run it; `app/api/games/[gameId]/operations/route.ts:122` keeps only `storySource` from the details. No code reads `respondentId` back. The player card (`app/player-dashboard.tsx:675`) says only "This is private to the moderators.", which is true.

**Reproduction.** In an in-memory game with fictional seats, post feedback as a player through the route, then call `collectGameBackup`. Join `pilotFeedback.id` to the `PILOT_FEEDBACK` event's `details_json.feedbackId`, read `respondentId`, look it up in `seats`. Observed: the match resolves to the sender ("Ana Fictional"). A permanent test asserts the join yields no seat id once the owner decides the rule.

**Fix.** Owner decision (Q3). Anonymous: stop writing `respondentId`. Attributable: change `guide/page.tsx:193` to match `:264`, and correct "audit log" in `:264`.

**Confidence.** Confirmed (reviewer and verifier). The verifier judged P2 right, not P1: only moderators can recover the sender, with a deliberate export and join, and the player card itself makes no anonymity promise.

### D25 · P2 · "Messages expire after N days" is not enforced, and backups keep chat forever

**What happens.** The console and guide say messages expire (7 days by default). Nothing does that on its own: the only purge runs when a moderator selects "Purge expired". `chat_rooms.expires_at` is never written. Every Export, Reset and Restore stores a full copy of all room messages (including the werewolf and Mason rooms) and the role assignments in `backup_exports.payload_json`, and no code deletes those rows. The purge also overwrites `purged_at` on messages a moderator already removed, so "Message removed by a moderator." becomes "Message expired." The false retention line is in the console and in the moderator section of the public guide; the player-facing screens make no retention claim.

**Where.** `app/moderator/ops-sections.tsx:135-136`; `app/guide/page.tsx:266`; `app/api/games/[gameId]/rooms/route.ts:136-150` (the only purge, with no `deleted_at IS NULL`); `lib/maintenance.ts:12-25` (covers sessions and rate limits only); `lib/chat/rooms.ts:22` (no `expires_at`); `lib/backup/snapshot.ts:79-88,129-142`; `app/moderator/room-history.tsx:42`.

**Reproduction.** Static: `grep -rn "expires_at" app lib` shows one read and no write; `grep -rn "'PURGED'" app lib` shows no writer; `grep -rn "DELETE FROM backup_exports" app lib` is empty. For the relabel: post a message, remove it as a moderator, run the purge with a retention of 0 days, read the room history; observed text flips to "Message expired.".

**Fix.** Owner decision (Q4). Either purge in `purgeExpiredRows` (join `games.chat_retention_days`) or reword to "Messages older than N days are removed when you select Purge expired."; add `AND deleted_at IS NULL`; add a retention rule for `backup_exports` (see D38).

**Confidence.** Confirmed (reviewer and verifier).

### D26 · P2 · Every player is told a Hunter is being eliminated before the result is published

**What happens.** When a locked phase calculates a result that eliminates the Hunter, the phase becomes `PENDING_HUNTER`. Until the moderator or the automation publishes, every Villager, Werewolf and spectator sees status `PENDING_HUNTER`, the label "Waiting for the Hunter", the headline "The village is holding its breath." and the Hunter's response deadline. A result with no Hunter in it shows only "Waiting for moderator review". After a Night the village can infer: the game has a Hunter, the pack's attack landed on the Hunter (or a lover of a victim) with no Bodyguard save; the wolves learn their target was the Hunter. The moderator can still override the list afterwards, so what players saw can be contradicted.

**Where.** `lib/game/phase-transitions.ts:189` (status chosen from `hunterRequiredIds`); `lib/game/engine.ts:317`; `lib/game/actions.ts:21-25` (label for non-Hunters); `lib/player/dashboard-data.ts:411-416`, `:479-483` (open phase spread into every player's payload) and `:580-583` (spectators); `app/player-dashboard.tsx:524`. Pending-approval states withdraw actions deliberately (`actionWithdrawn`, `dashboard-data.ts` about line 360); the pending-Hunter state takes no such care. Intent is mixed: the non-Hunter label dates from the original live-phase commit (`beb9a1e`, 2026-08-30).

**Reproduction.** In an in-memory game with a Hunter, lock a Day whose votes eliminate the Hunter, then call `loadDashboard` (`lib/player/dashboard-data.ts`) for a Villager and a Werewolf. Observed: `phase.status === 'PENDING_HUNTER'`, label "Waiting for the Hunter", `hunterDeadlineAt` present, `game.eliminatedPlayers` empty. The control (no Hunter in the result) gives `PENDING_APPROVAL` and "Waiting for moderator review". A permanent test asserts the control's output for every non-owing player.

**Fix.** Owner decision (Q1). For everyone except the Hunter who owes the shot, report `PENDING_APPROVAL` with "Waiting for moderator review" and omit `hunterDeadlineAt`.

**Confidence.** Confirmed (reviewer and verifier). The verifier corrected two supporting details: the test the reviewer cited (`lib/player/role-visibility.test.ts`, "leaves waiting states that every player shares") does not cover "Waiting for the Hunter", and `lib/game/console-guidance.ts:172` sits under the pending-approval case, not pending-Hunter. P2 stands, not P1: no player's role or per-player result is exposed, and everything inferable is published within hours.

### D27 · P2 · A Mayor's double vote can identify the Mayor from published data

**What happens.** The engine counts the Mayor's Day and Final ballot votes twice. The published ballot lists each voter once and the Village stats count one vote per voter ("votes received", leaders, "tied at the top", who was voted out). Example: Mayor p0 votes P2; p3 and p4 vote P1. The engine tally is P2=2, P1=2, a tie settled by the recorded draw (P2). Public data shows P1 with 2 votes and P2 with 1, no tiebreak flagged, and P2 voted out. Only a double vote explains it, and P2's only listed voter is the Mayor. The Mayor's identity is private (an ordinary shuffled role, off by default), and the guide says "The published ballot lists your vote once, like everyone else’s, and shows no vote totals."

**Where.** `lib/game/engine.ts:233` (weight 2); `app/guide/page.tsx:29`; `lib/game/game-stats.ts:192-199`, `:214-240`; `lib/player/dashboard-data.ts:75-97`, `:255-268`. A double vote that only breaks a public tie looks like the random draw, so only a flip of a strict public lead identifies the Mayor.

**Reproduction.** Call the engine on a Day where the Mayor (p0) votes P2 and p3 and p4 vote P1, with the recorded draw giving P2; then call `buildGameStats` (`lib/game/game-stats.ts`) on the same votes. Observed: leaders `['P1']`, top votes 2, voted out `['P2']`, `afterlifeBrokeTie` false.

**Fix.** Owner decision (Q2): soften `app/guide/page.tsx:29`, publish weighted counts or flag the Mayor's vote, or limit the double vote to ties.

**Confidence.** Confirmed (reviewer and verifier). Occasional: needs a Mayor in the composition and a decisive Mayor vote.

## 15. Checked and found sound at `d4aff81`

This is evidence at one commit, not an exemption: the next audit checks these again.

- **Origin, then authorization, then state, on every state-changing route.** A scripted sweep of all 43 mutating handlers found no violation. The two exceptions are by design: `email/unsubscribe` POST (token only; can only switch that seat's email off) and `scheduler/deadlines` (Bearer `CRON_SECRET`, compared as SHA-256 digests with `timingSafeEqual`, 503 when unset). Every handler under `games/[gameId]` authorizes before touching the database; owner-only actions (applications, co-moderator changes, cancel setup, reset, restore) check ownership; path and body IDs are always joined to the route's game.
- **Player and spectator reads.** On an open Night with wolf votes and a Seer inspection saved, none of eight players' dashboards nor a spectator's carried another living player's role or a forbidden key. Villager, Seer and spectator get 403 on the Werewolf room; another game's room is 403; a player of another game gets 404 on this game's phase routes; signed-out callers get 401. Timeline, votes and stats are built from an allowlist of public event types; roles are revealed inside the publish transaction (`lib/game/phase-transitions.ts:448`).
- **Sessions and secrets.** 256-bit random tokens with only the SHA-256 stored; seat and spectator sessions end when `session_version` changes (PIN reset, revoke, removal); co-moderator removal takes effect at once. PIN lockout survives cleanup and is cleared only by a correct PIN, a new claim or a moderator reset. Recovery codes are 72-bit, hashed, single use by compare-and-swap, and revoke all sessions. Backups exclude PIN and claim-code hashes, session tokens, password hashes and the public sign-up code; Restore regenerates claim codes and clears sessions. No secrets in tracked files or git history (pattern scan for provider key formats; `.env*` files not opened). No HTML-injection sinks; the invite CSV export escapes formula prefixes. `/api/*` responses carry `Cache-Control: private, no-store`; no CORS headers.
- **Atomic writes.** Every multi-step write followed is one `db.batch()` with the claim first and later statements repeating it; zero rows changed gives 409. The transient game statuses cannot persist outside one batch. Phase transitions (lock, finalize, publish) re-check state, version and the exact Hunter action inside the write; no ABA path was found. Roster edits claim by inserting their own event first.
- **Migrations.** Schema equals the 13 migrations for all 30 tables (columns, nullability, defaults, indexes, foreign keys). Every migration after the first is additive; the runner applies each migration and its version row in one batch and is rerun-safe.
- **Game rules.** Ties, no-vote results, protect versus attack, Mayor weighting, lovers, Hunter chains, Apprentice, parity and last-wolf wins held under the 30,000-case fuzz. Role assignment is a Fisher-Yates shuffle over `crypto.getRandomValues`; no `Math.random` or sort-based shuffle in game code. Deadline conversion matched a brute-force scan in 12 time zones. One harmless quirk: if "now" falls between the two occurrences of a repeated fall-back hour and the close time is in that hour, the next close skips to the next day. Dead players can only cast Afterlife votes; targets must be living. Automation sweeps are idempotent; a deadline cannot be extended once passed; there is no catch-up storm after a long gap.
