## 1. Summary for the owner

The code is carefully built where it matters most. Every multi-step write is one transaction, re-checks game state inside the write, and answers 409 when it loses a race. Every state-changing route checks the request origin and then the caller's permission before touching data. A scripted sweep of eight players' dashboards plus a spectator, on an open Night, found no other player's role. There is no P1 finding. Eleven P2 findings were raised and verified (D54 was reported by the owner). The owner has closed three (D24, D26 and D27) and two more are fixed and merged in pull request #90 (D54, a returning player who reuses a PIN across two games being refused at sign-in, and D22, one way to slow the server down without signing in). Six remain open: a guide sentence about feedback that needs rewording (D23), a retention promise the app does not keep (D25, to be reworded), and four player-facing screen problems (D62, D63, D64, D68). Verifiers lowered eleven other candidates to P3 and rejected none.

What needs attention:

1. **Everyone sees "Waiting for the Hunter" before the moderator publishes (D26).** When a calculated result eliminates the Hunter, every player's screen switches to "Waiting for the Hunter" with a countdown. After a Night this tells the whole village that the wolves' victim was the Hunter and the Bodyguard did not stop it, hours before the result is public, and a moderator override can later contradict what they saw. **Closed on October 5: the owner decided this beat is intended**, since the Hunter's shot follows soon after.
2. **A Mayor's double vote can give the Mayor away (D27).** When the Mayor's second vote flips a strict public leader, the published numbers cannot be explained any other way. **Closed on October 5: the owner is fine with the current wording.**
3. **Three promises about privacy and backups do not hold (D23, D24, D25).** The guide tells players moderators cannot see who sent feedback, but a backup export links each feedback to a seat. The console says Reset and Restore preserve a backup, but spectators' Afterlife chat is deleted and was never in it. "Messages expire after N days" does not happen by itself, and every backup keeps private chat forever. Owner decisions on October 5: D23 is fixed by rewording the guide, not by code; D24 is accepted as it is; D25 is still open.
4. **One sign-in request can freeze a server instance (D22).** A crafted email in the seat sign-in form takes over a second of processor time at 32,000 characters and grows quadratically, before any rate limit applies. No account is needed. **The owner has made this the top priority.**
5. **Reusing a PIN across two games blocks sign-in (D54, reported by the owner).** A player who picks the same PIN for a new game as for an earlier one, even a finished one, is refused at email sign-in with a message asking for the seat code. Finished games should never count against a running one. **Fixed in pull request #90, merged on October 6.**
6. **Four player-facing screen problems (D62, D63, D64, D68).** A "Response saved" message carries into the next phase's ballot; "Closing now" is shown for as long as the moderator takes to review a result; moderator Sign out leaves every role on screen until the page is reloaded; and a failed refresh is invisible while a player waits and stuck once they act. All four were traced in the code but not run in a browser, because the project has no browser or component test harness for them.
7. **Lower priority:** 94 P3 items, including an unchanged "nothing new" poll doing as much database work as a full one (E11), sign-in timing that reveals which emails have accounts (D28), weak six-digit PINs allowed (D30), migration and setup scripts that never say which database they touched (D45), game-rule gaps in extreme settings (D39, D40, D41), and dead columns in the schema (R12).

Verified reassurances only: no finding exposes one player's role or a per-player private result (Seer inspection, for example) to another player. D26 and D27 leak indirect facts, not a named player's role.

## 4. Defects

Priority: **P1** exposes private data or opens a security hole; loses or corrupts data; leaves a core flow stuck with no way out; or tells users something false about their privacy or safety. **P2** wrong behavior or wrong user-visible text in a working flow; an operational gap that would hurt a real session; a doc that would lead an operator into a harmful step. **P3** hardening, cleanup, and wording that won't mislead anyone into harm.

### D22 · P2 · One unauthenticated sign-in request can freeze a server instance

> **Owner decision (October 5): fix it; top priority.** The change is small: refuse identifiers longer than 254 characters before any pattern runs. Making the changes goes through the normal `fix/` branch workflow.
>
> **Status.** Fixed and merged: pull request #90, merge commit `64f546f` on `version-1.14` (commit `6cb9ac9`, branch `fix/signin-length-and-multi-game-signin`): identifiers over 254 characters are refused with the generic 401 before any pattern or the rate limiter runs, the email check is now linear-time (a unit test compares it with the old pattern on every string up to 6 characters over a small alphabet), and moderator recovery has the same cap. `npm run verify` passed (85 test files, 891 tests, lint, typecheck, build, 0 vulnerabilities). The Preview is ready; the screens have not been checked in a browser.

**What happens.** `POST /api/seats/login` tests the identifier against an email pattern before the rate limiter runs. The pattern backtracks quadratically on a long string of dots. Anyone can send one request and tie up a Vercel function instance; during a live phase that stalls players and the moderator on that instance. Availability only; no data is exposed.

**Where.** `lib/roster/email-address.ts:4-5` (pattern); `app/api/seats/login/route.ts:39` (pattern runs) before `:41` (`enforceRateLimit`). The same pattern runs in `lib/auth/moderators.ts:77` (recovery), where the limiter keys only the first 80 characters of the email (`app/api/moderators/recover/route.ts:14`), so varying those characters avoids it. Nothing bounds the body or the identifier length earlier (`proxy.ts`, `next.config.ts`, `vercel.json`).

**Reproduction.** In a Vitest file, call the `POST` handler of `app/api/seats/login/route.ts` with a same-origin request and body `{"identifier":"a@" + ".".repeat(N) + ",","pin":"123456"}`. Time it. Observed at `d4aff81`: N=16,000 about 0.33 s, N=32,000 about 1.06 s, status 401. The bare pattern alone: 8k 66 ms, 16k 263 ms, 32k 1,033 ms, 64k 4,176 ms. A permanent test asserts that N=32,000 finishes in under 50 ms and that identifiers over 254 characters are refused.

**Fix.** Reject identifiers longer than 254 characters before any pattern (`lib/game/signups.ts:68` already does), in `seats/login` and `redeemModeratorRecoveryCode`; also make the pattern linear.

**Confidence.** Confirmed (reviewer and verifier).

### D27 · closed · A Mayor's double vote can identify the Mayor from published data

> **Owner decision (October 5): the current wording is fine; no change. Closed.** The finding stays here as a record of what the published ballot reveals when a Mayor's second vote flips a clear public leader.

**What happens.** The engine counts the Mayor's Day and Final ballot votes twice. The published ballot lists each voter once and the Village stats count one vote per voter ("votes received", leaders, "tied at the top", who was voted out). Example: Mayor p0 votes P2; p3 and p4 vote P1. The engine tally is P2=2, P1=2, a tie settled by the recorded draw (P2). Public data shows P1 with 2 votes and P2 with 1, no tiebreak flagged, and P2 voted out. Only a double vote explains it, and P2's only listed voter is the Mayor. The Mayor's identity is private (an ordinary shuffled role, off by default), and the guide says "The published ballot lists your vote once, like everyone else’s, and shows no vote totals."

**Where.** `lib/game/engine.ts:233` (weight 2); `app/guide/page.tsx:29`; `lib/game/game-stats.ts:192-199`, `:214-240`; `lib/player/dashboard-data.ts:75-97`, `:255-268`. ## 15. Checked and found sound at `d4aff81`

This is evidence at one commit, not an exemption: the next audit checks these again.

- **Origin, then authorization, then state, on every state-changing route.** A scripted sweep of all 43 mutating handlers found no violation. The two exceptions are by design: `email/unsubscribe` POST (token only; can only switch that seat's email off) and `scheduler/deadlines` (Bearer `CRON_SECRET`, compared as SHA-256 digests with `timingSafeEqual`, 503 when unset). Every handler under `games/[gameId]` authorizes before touching the database; owner-only actions (applications, co-moderator changes, cancel setup, reset, restore) check ownership; path and body IDs are always joined to the route's game.
- **Player and spectator reads.** On an open Night with wolf votes and a Seer inspection saved, none of eight players' dashboards nor a spectator's carried another living player's role or a forbidden key. Villager, Seer and spectator get 403 on the Werewolf room; another game's room is 403; a player of another game gets 404 on this game's phase routes; signed-out callers get 401. Timeline, votes and stats are built from an allowlist of public event types; roles are revealed inside the publish transaction (`lib/game/phase-transitions.ts:448`).
- **Sessions and secrets.** 256-bit random tokens with only the SHA-256 stored; seat and spectator sessions end when `session_version` changes (PIN reset, revoke, removal); co-moderator removal takes effect at once. PIN lockout survives cleanup and is cleared only by a correct PIN, a new claim or a moderator reset. Recovery codes are 72-bit, hashed, single use by compare-and-swap, and revoke all sessions. Backups exclude PIN and claim-code hashes, session tokens, password hashes and the public sign-up code; Restore regenerates claim codes and clears sessions. No secrets in tracked files or git history (pattern scan for provider key formats; `.env*` files not opened). No HTML-injection sinks; the invite CSV export escapes formula prefixes. `/api/*` responses carry `Cache-Control: private, no-store`; no CORS headers.
- **Atomic writes.** Every multi-step write followed is one `db.batch()` with the claim first and later statements repeating it; zero rows changed gives 409. The transient game statuses cannot persist outside one batch. Phase transitions (lock, finalize, publish) re-check state, version and the exact Hunter action inside the write; no ABA path was found. Roster edits claim by inserting their own event first.
- **Migrations.** Schema equals the 13 migrations for all 30 tables (columns, nullability, defaults, indexes, foreign keys). Every migration after the first is additive; the runner applies each migration and its version row in one batch and is rerun-safe.
- **Game rules.** Ties, no-vote results, protect versus attack, Mayor weighting, lovers, Hunter chains, Apprentice, parity and last-wolf wins held under the 30,000-case fuzz. Role assignment is a Fisher-Yates shuffle over `crypto.getRandomValues`; no `Math.random` or sort-based shuffle in game code. Deadline conversion matched a brute-force scan in 12 time zones. One harmless quirk: if "now" falls between the two occurrences of a repeated fall-back hour and the close time is in that hour, the next close skips to the next day. Dead players can only cast Afterlife votes; targets must be living. Automation sweeps are idempotent; a deadline cannot be extended once passed; there is no catch-up storm after a long gap.
- **Guide statements checked and true:** the slot table (1 to 30 players: 1; 31 to 60: 2; 61 to 80: 3), win conditions, Night ties by random draw, the 8-hour Hunter window default, deadlines extend but never shorten, Masons zero or at least two, Cupid pairs once and may include themselves, the Bodyguard cannot protect themselves.
- **Build and config.** `next.config.ts`, `tsconfig.json` and `eslint.config.mjs` do not weaken checks: no skipped type or lint errors, `strict: true`, no `@ts-ignore`, `@ts-expect-error` or `@ts-nocheck`, 3 non-test `any`, and 5 scoped, explained `eslint-disable` lines in `app/`. `drizzle.config.ts` has no credentials, so `drizzle-kit migrate` and `push` cannot reach a database. `db/index.ts` refuses `file:` and `:memory:` URLs when `VERCEL=1` or `NODE_ENV=production`. All Vitest API tests run on in-memory `node:sqlite` and never read `TURSO_DATABASE_URL`. `playwright-server.mjs` forces a disposable local database and deletes it on exit; `run-playwright.mjs` refuses a remote base URL in local mode; the remote preflight requires https, an exact origin, a Preview deployment in READY state and the project name. No script prints secrets other than the intended one-time recovery codes. `CRON_SECRET` fails closed (503 when unset, 401 when wrong, compared by digest).
- **Polling and caching.** `lib/http/poll-while-visible.ts` skips hidden tabs, refreshes once on return, stops players after 5 idle minutes and at game end, and adds 20% jitter; polls switch to 10 s only within 15 minutes of an open phase's deadline. A poll with nothing due costs the automation sweep one query and no writes; the closing reminder is claimed by a compare-and-swap update so concurrent polls send at most one. Payloads carry no per-request values (the 304 repeat held for player, phases, operations, stats, choices and games). Timeline queries are index-hinted and capped at 100 events, notifications at 25, backups at 12. `ensureDatabase` runs its readiness query once per cold start. The guide video preloads metadata only with a poster; the 14 guide screenshots are WebP (809 KB) through `next/image`; page-specific client chunks are 91 KB raw (27 KB gzip) for the player page, 175 KB (47 KB) for the moderator page, 58 KB (17 KB) for the landing page and 37 KB (11 KB) for the guide.
- **Entry points and notifications.** Error bodies for database and library failures are generic (`lib/http/errors.ts:26-35`; a plain `Error` thrown by app code is shown as written with a 400, see the pass 3 note in section 12); result, open and reminder email recipients are limited to claimed seats of that game with email on; the result-story input is public-only, the AI call has a 20-second timeout with no retries and falls back to a template; the closing reminder is claimed by a conditional update; the public join flow replies the same for known and unknown emails and has a honeypot and size caps; unsubscribe needs its token, is idempotent and rate-limited; the invites route sends one plain address per seat and checks the mailer before replacing any link; chat access needs room membership in the same game, spectators reach only the Afterlife and Town Hall, and a lost insert race returns 409; player sign-in clears the spectator cookie and the reverse; a racing second seat claim gets 409 and no session.
