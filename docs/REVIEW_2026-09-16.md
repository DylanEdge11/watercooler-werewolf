# Watercooler Werewolf review — September 16, 2026

**Verdict: continue with fictional testing; do not sign off for real games yet.** The existing quality gates pass, but this review reproduced four defects and identified three additional issues in the source. The most serious defect exposes private Night information to other authenticated players in the same game.

Reviewed source: [main at 58e5aec](https://github.com/DylanEdge11/watercooler-werewolf/commit/58e5aec4a7ba53407e1f70c4da19000a2281cf01).

Only documentation is changed by this review: `README.md` and this report. Application code, configuration, dependencies, migrations, and checked-in tests are unchanged. No deployment, real invitations, or hosted game mutations were performed.

### R1 — P1: Shared timeline exposes private Night information

**Location:** [player response, line 218](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/app/api/player/route.ts#L218), with the full outcome written by [phase publication](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/app/api/games/%5BgameId%5D/phases/route.ts#L664).

Publication stores complete `proposedOutcome` and `publishedOutcome` objects in a `PHASE_PUBLISHED` event. The player endpoint returns that event's entire parsed payload. Those outcome objects include investigations, Seer seat IDs, investigation targets and exact roles, protection targets, and Night vote tallies.

The screen displays only selected fields, but the hidden fields are still available in the authenticated player's HTTP response. This is a server-side privacy failure; hiding more UI elements will not fix it. It does not require moderator access.

**Reproduction:** in an isolated 20-seat game, a Seer investigated a living Werewolf, the Bodyguard protected an attack target, and the Night was published. A different player with role `VILLAGER` received:

```json
{
  "privateData": [
    { "seerId": "p1", "targetId": "p17", "role": "WEREWOLF" }
  ],
  "protected": ["p3"]
}
```

These are fictional test identifiers. No participant was eliminated in that protected attack, so the role information was not an intended elimination reveal.

**Required correction:** construct an explicit player-safe event payload containing only approved public fields, such as phase kind, public eliminations, and winner. Keep full calculations in moderator/audit responses and Seer results in that Seer's notifications. Apply filtering when reading existing events too.

**Acceptance check:** publish Night results, then inspect the full JSON as an ordinary Villager, a Werewolf, and the Seer. Unauthorized players must receive no investigation identities/results or other private Night details; the Seer must retain their own result.

### R2 — P1: Hunter override does not enable the player's action

**Location:** [Hunter permission calculation, line 67](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/app/api/player/route.ts#L67).

The player dashboard reads `outcome_json`, the original engine proposal. A moderator override is stored in `reviewed_outcome_json`. The action-submission route correctly uses the reviewed outcome, so the two endpoints disagree.

**Reproduction:** calculate a Day with no elimination, override it to eliminate the Hunter, then request the Hunter's dashboard. The phase is `PENDING_HUNTER`, but the response is:

```json
{
  "permission": {
    "actionKind": null,
    "maxTargets": 0,
    "label": "Waiting for the Hunter"
  },
  "candidates": []
}
```

The Hunter cannot make the shot through the normal interface. Waiting for the timeout lets moderation proceed but unfairly removes the player's opportunity.

**Required correction:** use the authoritative reviewed outcome, falling back to the original proposal, for both Hunter permission and candidate exclusion.

**Acceptance check:** cover ordinary Hunter elimination, an override that introduces a Hunter, and an override that changes the other elimination targets. The UI and submission route must agree on both permission and legal targets.

The ordinary Hunter flow passed the additional checks. The checked-in rehearsal misses the override bug because it checks the phase status and then submits directly through the action API without asserting the dashboard's permission or candidates.

### R3 — P2: Reset brings archived players back into the roster

**Location:** [Reset seat update, line 210](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/app/api/games/%5BgameId%5D/operations/route.ts#L210).

Roster replacement preserves old seats as `REMOVED` for audit references. Reset updates **every** seat in the game to `INVITED` and living, including those archived rows.

**Reproduction:** a game with 20 current seats and one archived seat was Reset. The archived seat became `INVITED`, and a newly collected backup counted 21 current seats. Repeated roster replacements can make the effect larger and can exceed the 80-player restore limit.

**Required correction:** preserve the archived state of removed seats while still invalidating credentials and sessions as needed. Reset only the current roster into invited setup state.

**Interim operating guidance:** after Reset, immediately re-import the intended roster before assigning roles or taking another setup backup. Retain the pre-Reset backup.

**Acceptance check:** replace a roster multiple times, Reset, and verify current counts, backup filtering, and Restore all retain exactly the intended current players while preserving archived audit references.

### R4 — P2: An in-flight chat message can be saved after Stop

**Location:** [message write, line 63](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/app/api/rooms/%5BroomId%5D/messages/route.ts#L63).

The route checks room access before writing. Its eventual message insert is unconditional and does not recheck room status, game status, or membership in the same transaction.

**Reproduction:** pause an authorized Werewolf's message request after it reads an open room; run the actual Stop route; resume the message request. The game was `STOPPED` and the room read-only, yet the response was **201 Created** and one message was inserted.

This demonstrates one request crossing the Stop boundary, not an unlimited ability to chat after Stop.

**Required correction:** condition the insert on current room/membership/game authorization at commit time, and write the audit event only if the message insert succeeds.

**Acceptance check:** repeat the interleaving for Stop, a room lock, and elimination of a faction member. A request that loses write access must not save a message or report success.

### R5 — P2: No second-game creation or game selection in the console

**Location:** [conditional creation form, line 351](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/app/moderator/page.tsx#L351), and [automatic game selection](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/app/moderator/page.tsx#L123).

The creation form is rendered only when `games.length === 0`. Although the API supports multiple games, there is no visible selector or new-game action. On a fresh page load, the newest assigned game is chosen automatically.

This blocks the ordinary website workflow for retaining an old campaign while starting another. Helpers can also create additional games that the moderator cannot switch between through the console.

**Required correction:** add explicit game selection and an always-available authorized create-game workflow. Clear game-specific drafts and invitation downloads when switching.

**Acceptance check:** create two games, switch between them, reload each selection, and verify operations, roles, and invitations stay attached to the selected game. This still needs a browser test.

### R6 — P2: Background refresh overwrites unsaved role counts

**Location:** [assignment refresh, line 116](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/app/moderator/page.tsx#L116), triggered by [ten-second polling](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/app/moderator/page.tsx#L157).

The numeric inputs edit `composition`. Every background refresh unconditionally replaces that same state with the saved server composition. A moderator who takes more than a polling interval to adjust several role counts can lose their draft.

**Required correction:** track a separate draft or dirty state and preserve local edits during polling. Refresh the draft after a successful save, explicit discard, or game switch.

**Acceptance check:** change multiple counts, wait at least 15 seconds, and verify the draft remains. Save and confirm the resulting assignment uses the intended counts. Browser reproduction remains pending.

### R7 — P2: Scheduler configuration example names an unused secret

**Location:** [.env.example, line 15](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/.env.example#L15), compared with [scheduler configuration, line 8](https://github.com/DylanEdge11/watercooler-werewolf/blob/58e5aec4a7ba53407e1f70c4da19000a2281cf01/app/api/scheduler/deadlines/route.ts#L8).

The example suggests `SCHEDULER_SECRET`; the implementation reads only `WATERCOOLER_SCHEDULER_TOKEN`. Following the example literally leaves the endpoint disabled with HTTP 503.

**Required correction:** align the example with the implemented variable. The README now names the correct variable; configuration was left unchanged under the instruction not to modify code.

**Acceptance check:** configure the correct Worker binding in an isolated environment. Verify missing configuration returns 503, invalid authentication returns 401, and a correctly authenticated request locks due phases without opening or publishing new phases.

### What the additional checks established

The temporary checks called the actual application route functions with a fresh in-memory SQLite database populated through the checked-in SQL migrations. They used a D1-compatible adapter and isolated test identities; session authentication and room synchronization were mocked, following the existing route-test style. They are not tests of the deployed authentication gateway or the complete Cloudflare runtime.

The three passing checks covered:

- An ordinary Hunter elimination, player action, finalization, and publication.
- Entry into Final Showdown followed by a Final Ballot that completes the game with a Village win.
- A backup without credential fields, followed by Restore that issues 20 fresh invites and clears active roles.

The four failing checks verified that the desired privacy, override, archived-roster, and Stop/chat guarantees are not currently met. Reproduction steps and expected corrections are recorded above. The temporary test harness was kept outside the project; no tests were added to the repository.

### What could not be verified here

`npm run dev -- --host 127.0.0.1` failed before startup when Cloudflare's preview tooling called `os.networkInterfaces()`, returning `ERR_SYSTEM_ERROR / uv_interface_addresses`. This is an environment limitation, not evidence that the application cannot start on the intended host. No application or dependency code was patched to work around it.

Consequently, this pass does not certify:

- The current hosted version matching the reviewed GitHub commit.
- First-owner verification, browser cookie handling, or hosted authentication/header trust.
- A full authenticated game across real browser sessions.
- Mobile layout, keyboard navigation, screen-reader behavior, or reconnect behavior.
- Live scheduler configuration, hosting-specific migrations, deployment rollback, or recovery after complete database loss.
- Load/performance readiness or every possible concurrent operation.

Existing tests cover useful engine, timezone/DST, migration, credential, setup, and phase-race cases. Their success is narrower than a guarantee that every feature works.

## Documentation changes

The README now provides separate real-game and fictional-test workflows with actual button names. It explains invitation delivery, keeping the seat code for repeat login, all-seat claiming, role release, manual phase operation, Hunter follow-up, Final Showdown, and recovery.

It also clarifies that:

- There is no test-mode flag or automatic email delivery.
- Schedules do not open or publish phases automatically.
- The helpers need the actual test-account credentials in their shell environment.
- Completing browser moderator creation is preferable to relying on helper bootstrap; the helper does not carry the browser's owner session and discards returned recovery codes if its bootstrap branch succeeds.
- The two helpers create separate games, and the rehearsal itself performs mutations without checking `PILOT_ALLOW_MUTATION`.
- Reset is not a pause, and Restore is a setup rebuild rather than a return to a saved round.
- The Restore UI uses snapshots stored in the database; an exported JSON download is not an implemented full disaster-recovery import workflow.

Historical status and supporting documents were retained. Their earlier broad privacy/readiness statements must be read alongside this review.

## Recommended next work

Fix R1 and R2 first and add regression coverage that asserts the entire player response, including permissions and hidden JSON fields. Address R3–R7, then rerun the existing gates and these reproductions.

After those fixes, complete one disposable hosted 20-player game with distinct moderator/player sessions. Include every role, late actions, private-room access, both faction win conditions, Final Showdown, credential recovery, Stop, Reset, and Restore. Confirm the deployed source version and perform the pending mobile/accessibility checks before using a real roster.
