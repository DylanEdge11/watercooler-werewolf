### Found while fixing

- An unmigrated database answered 401 on every API route, so the release check "5xx means not migrated" could never fire. It now answers 503 (#37).
- Between phases, the dashboard's Cycle counter showed 00 (#47).
- A server-rendered dashboard dropped a target picked before its first refresh returned (#52).

## 1. Summary for the owner

The foundations are sound. Every rule change is a guarded, all-or-nothing database write. The player API only sends fields that are safe for players. The test suite is broad (266 unit tests, 20-player bot games, browser runs), and all five fast gates pass on the candidate.

What needs attention:

1. **Two ways a game can get stuck around the Hunter** (D1, D2). Both were reproduced. Both carry over unchanged into PR #34, where the automatic sweep would repeat them on its own. Fix them before PR #34 merges.
2. **Some visible wording is wrong or confusing** (D3–D5): the Seer's result reads "Ana is the WEREWOLF.", the first Night's nudge says "Night 2", and a Mayor's vote can make the public tally disagree with the result.
3. **Refreshing a page writes to the database** (E1). Every 10-second player refresh runs two write transactions and about 16 database round trips, one after another. This is the main cost at 80 players. It is also the first task of the September 25 performance audit, which was never merged; it was added to this branch as `docs/PERFORMANCE_AUDIT.md` (since removed; see Git history).
4. **Housekeeping.** Duplicated helpers and types, schema fields that nothing uses, error responses that return the wrong status, and docs that no longer match the code. None of these breaks a game.

No finding exposes a player's role or private result to another player.

## 4. Defects

Priority: **P1** fix before the 1.4 release (and before PR #34 merges), **P2** fix in 1.4 if it fits, **P3** backlog.

### D1 · P1 · An invalid Hunter shot keeps the phase waiting for the Hunter forever

**What happens.** If a Hunter's saved shot becomes invalid (for example, its target is already in the result), `resolveHunterShot` records a warning but leaves `hunterRequiredIds` set (`lib/game/engine.ts:240-262`). "Finalize Hunter" then moves the phase to `PENDING_APPROVAL` with that outcome. "Approve & publish" sees a Hunter still required (`app/api/games/[gameId]/phases/route.ts:611`) and sends the phase back to `PENDING_HUNTER` with a fresh deadline, and the cycle repeats. "Skip Hunter" doesn't break the loop, because it only applies when no shot exists (`route.ts:524`, `:549`).

**How to reach it (reproduced).** A Day eliminates the Hunter. The Hunter shoots P1. Finalize. The moderator overrides the result to eliminate the Hunter *and* P1. The override re-enters `PENDING_HUNTER` and re-uses the old shot at P1, which is now "already eliminated". From then on, Publish → `PENDING_HUNTER` → Finalize → `PENDING_APPROVAL` → Publish, indefinitely. With PR #34 in Automatic mode, the sweep drives this loop by itself.

**Workaround today.** Override to eliminate only the Hunter. The saved shot at P1 is then valid and applies.

**Fix.**
1. In `resolveHunterShot`, treat an invalid shot like no shot: clear `hunterRequiredIds` and keep the warning. The moderator can still override.
2. When an override hands the phase back to `PENDING_HUNTER`, supersede any existing `HUNTER_SHOT` for that phase in the same batch, so the Hunter chooses again against the new result.
3. Test at route level: the recipe above must end in `PUBLISHED` after one Finalize and one Publish.

### D2 · P1 · "Finalize Hunter" can strand a phase with no way out

**What happens.** Finalize claims the phase with a separate write (`HUNTER_FINALIZING`, `route.ts:528-537`), then reads players and actions, then writes the result in a batch (`route.ts:568-579`). Any error or timeout between the claim and the batch leaves the phase in `HUNTER_FINALIZING`: a database blip, a malformed stored override, or a function timeout. Nothing accepts that state. Opening a phase refuses while it exists (`route.ts:345`), Finalize needs `PENDING_HUNTER`, and Publish needs `PENDING_APPROVAL`. Only Stop or Reset clears it, and both end the game. PR #34 keeps this code and runs it inside player page loads, which makes a timeout more likely.

**Fix.** Make the claim part of the result batch, the way Publish's `PUBLISHING` claim is: compute the outcome first against the read `version`, then send one batch whose first statement moves `PENDING_HUNTER` to `PENDING_APPROVAL` on `version = ?`, with the other statements guarded on it. Keep `HUNTER_FINALIZING` only if something still needs it. Add a test that injects a failure between the reads and the write and checks that the phase is still `PENDING_HUNTER`.

### D3 · P2 · The Seer's result shows a raw role code

`"${name} is the ${investigation.role}."` (`route.ts:746`) produces "Ana is the WEREWOLF." and "Ben is the APPRENTICE_SEER." Use `ROLE_CATALOG[role].name`, and update the assertions in `e2e/scripted-20-player.spec.ts:92,100` that expect the raw code. `readableRole()` in `lib/game/timeline-view.ts` already does this for the timeline.

### D4 · P2 · Phase numbers are counted per phase, not per Day/Night pair

`phases.sequence` increases for every phase (Day 1 = 1, Night 1 = 2, Day 2 = 3). The nudge message uses it directly (`lib/game/moderator-copy.ts:31,33`), so the first Night's group-chat text says "Night 2" and the second Day says "Day 3 ballot". The dashboard and console label the same number "Cycle", so a Day and the Night after it are shown as different cycles. Add one helper (for example `cycleNumber(sequence) = ceil(sequence / 2)` for Day and Night phases, with Final ballots numbered separately) and use it in the nudge, the dashboard eyebrow, the vote modal title, the console, and the timeline. Reproduced as a unit test.

### D5 · P2 · A Mayor's vote can make the public tally disagree with the result (decided: hide totals)

The engine counts a Mayor's Day vote twice. The full Timeline shows unweighted per-target totals (`tallyVotes` in `lib/game/timeline-view.ts:122`, used in `app/full-timeline.tsx:25`). When the Mayor's vote forces a tie and the draw goes their way, players see for example "Ana 3, Ben 2, Ben eliminated". That looks like a bug, and it tells players one of Ben's two voters is the Mayor. The guide promises "your role stays hidden" (`app/guide/page.tsx:28`). Reproduced as a unit test.

**Fix (owner decision).** Remove the per-target totals from the full Timeline and keep the ledger of who voted for whom. Update the guide: line 28 (the Mayor's card) and line 171 ("with each Day's vote tally").

### D6 · P2 · Docs call feedback anonymous, but it is not (decided: identified is fine)

Each feedback submission writes the sender's seat or moderator ID into `operational_events` (`app/api/games/[gameId]/feedback/route.ts:70`). That table is returned by the Operations API and included in every backup. Keep the behaviour and fix the text that says otherwise: `docs/TECHNICAL.md:63` ("the table stores no respondent id"), `docs/OPERATIONS.md:24` and `app/guide/page.tsx:208` ("never who"), and any matching console help text. The player's card says "private to the moderators", which stays accurate.

### D7 · P2 · Room access is updated after publication, not inside it

`docs/TECHNICAL.md:48` says publishing "updates room access … in one transaction". In the code, `ensureGameRooms` runs after the batch commits (`route.ts:796`; the same pattern follows role release in the assignments route). If it fails, the moderator sees an error for a publish that actually succeeded. A retry takes the idempotent path, which doesn't call `ensureGameRooms`. Today the next player refresh repairs membership, because every player GET calls `ensureGameRooms` (E1). **Once E1 removes that call, this becomes a real gap:** a newly eliminated player might never get the Afterlife room. Chat posting re-checks role and alive status (`app/api/rooms/[roomId]/messages/route.ts`), so no one can write where they shouldn't.

**Fix, together with E1.** Put the membership upserts in the publish and release batches, or call `ensureGameRooms` on the idempotent publish path too. Then correct the doc sentence.

### D8 · P2 · Error responses use one status for every failure and pass through internal messages

Most routes wrap everything in one `try/catch` with a fixed status. GET handlers return 401 for any error (`operations/route.ts:98`, `phases/route.ts:219`, `feedback/route.ts:28`, `games/route.ts`, and others), so "not a moderator of this game" (should be 403), "game not found" (404), and a database outage (500) all look like "sign in again". POST handlers return 400 for authorization failures and server errors alike. The raw `error.message` goes to the client, including libSQL error text. `app/api/moderators/logout/route.ts` has no `try/catch`, so a bad Origin header returns 500.

**Fix.** Have the auth helpers and state checks throw a small `HttpError(status, message)`. Add one `routeError(error, fallback)` that maps known errors and returns a generic message (while logging the real one) for anything unexpected. Apply it route by route. Unit test the mapper.

### D9 · P3 · Some multi-step writes are not one transaction

CLAUDE.md says multi-statement writes use `db.batch()`. Exceptions:

- Seat claim: the `UPDATE … RETURNING`, the `SEAT_CLAIMED` event, and the session insert are three separate writes (`app/api/seats/claim/[code]/route.ts`).
- Action submission: the `ACTION_SUBMITTED` event and the version read happen after the batch (`app/api/phases/[phaseId]/actions/route.ts`).
- Release and publish: `ensureGameRooms` runs after the batch (D7).
- Finalize Hunter: the claim is a separate write (D2).
- Reset and Restore: the safety backup is written before the batch, so a 409 leaves an extra backup. This one is harmless.

The main risk is a missing audit event. Fold the event inserts into the batches (use `RETURNING` for the version).

### D10 · P3 · Game creation stores the schedule unvalidated and duplicates validation

`POST /api/games` stores `JSON.stringify(body.schedule)` exactly as sent (`app/api/games/route.ts:130`), so any extra keys persist. `PATCH …/schedule` keeps only `dayCloses` and `nightCloses`. Neither route checks the final cutoff against the start and end dates. The two routes repeat about 25 lines of validation. Move it into one `validateGameSetup()` in `lib/game/`, normalize the schedule in both routes, and unit test it.

### D11 · P3 · The override input isn't type-checked

A non-array `overrideEliminationIds` throws `…filter is not a function`, and that text reaches the client as the error (`route.ts:601`). Validate that it is an array of strings first.

### D12 · P3 · A divisor of 1 or 2 is allowed

`lib/game/game-settings.ts` accepts divisors from 1 to 80. A divisor of 1 makes the slot count equal the number of living players, so everyone who receives a vote is eliminated in one phase. Consider a floor (for example 5), or a confirmation when the slot preview shows more than a few slots.

### D13 · P3 · Sessions and rate-limit rows are never cleaned up

Nothing deletes expired `moderator_sessions`, `seat_sessions`, or old `rate_limit_buckets` rows. Bucket keys include client-supplied text: `moderator-login:${email}` (`app/api/moderators/login/route.ts:13`) has no length cap, so a caller can create rows at will. Cap key parts at 80 characters, as seat login already does. Add a cleanup step to the scheduler route, for example: delete sessions past `expires_at` and buckets older than a day.

### D14 · P3 (P2 before the first paying company) · PIN guessing is only limited per IP

Seat sign-in allows 8 attempts per 15 minutes per identifier *per IP*. A six-digit PIN has a million values, so guesses spread across many IPs are not bounded per player. Add a per-seat daily ceiling that tells the player to ask their moderator for a new PIN.

### D15 · P3 · The password-hashing comment is wrong, and moderator sign-in reveals whether an account exists

`lib/auth/crypto.ts:3` says raising the PBKDF2 iteration count "would make old accounts impossible to verify". It wouldn't: each stored hash records its own count, and `verifySecret` reads it. New hashes can use OWASP's 600,000 iterations while old ones still verify. Separately, `authenticateModerator` returns early for an unknown email, so response time shows whether an account exists. The rate limit makes this low risk. Run a dummy verify on the miss path.

### D16 · P3 · The scheduler secret is compared with `!==`

`app/api/scheduler/deadlines/route.ts:25`. Compare in constant time instead (hash both values and compare the digests, or use `timingSafeEqual`).

### D17 · P3 · `SITE_ORIGIN` is documented as required but is optional in code

`docs/SETUP.md:30` marks it required. `assertSameOrigin` falls back to the request's own origin when it is unset. Claim links always use the request origin, never `SITE_ORIGIN`. Pick one: fail fast at startup when it is missing in a deployment, or mark it optional in the doc.

### D18 · P3 · Reset keeps announcements; Restore deletes them

After a Reset, the moderator's "Announcement copy" still lists the previous run's announcements (`app/api/games/[gameId]/operations/route.ts`, Reset branch; compare `lib/backup/snapshot.ts:210`). Players don't see them, because the timeline starts at the reset. Make Reset delete announcements too, or document the difference in `docs/OPERATIONS.md`.

### D19 · P3 · Co-moderators can't be removed, and ownership can't be transferred

There is no route for either. This is an operational gap to close before the first paying company.

### D20 · P3 · Backups are not a consistent snapshot

`collectGameBackup` runs 17 reads in parallel outside a transaction (`lib/backup/snapshot.ts`). A write that lands in the middle can produce a backup that disagrees with itself (for example, an action without its phase). Read in one `read` batch, or check afterwards that `games.updated_at` didn't change.

### D21 · P3 (decided) · Backups live in the game database

Automatic backups are rows in `backup_exports` in the same Turso database. For the pilot, add a sentence to `docs/OPERATIONS.md#backups` saying so, and saying that recovery from a lost database uses Turso's point-in-time restore plus any JSON file a moderator downloaded. Before the first paying company, add a scheduled export outside Turso.

## 8. PR #34 (`feat/auto-publish`): fix before merge

The extraction into `lib/game/phase-transitions.ts` is the right shape, and the automation rule in `lib/game/automation.ts` is small, pure, and tested. Before it merges into `version-1.4`:

1. **Default new games to Review** (owner decision): `DEFAULT_NEW_GAME_AUTOMATION` and the setup form default; update the guide and OPERATIONS text that says new games publish automatically.

## 11. Checked and sound

So later sessions don't re-audit them:

- **Player privacy.** `/api/player` whitelists every timeline payload field, strips proposed and reviewed outcomes, tallies, protection, and investigations, and returns roles only for eliminated players and the player's own teammates. The participation counter can't reveal Night-role counts. `FORBIDDEN_PLAYER_KEYS` is enforced by the browser suite.
- **Concurrency.** Setup edits, release, open, lock, publish, stop, reset, restore, seat claim, and invite rotation all use guarded writes with 409 on zero changes. Race tests cover them.
- **Origin and auth order** on every mutating route. Session cookies are HTTP-only, SameSite=Lax, and Secure in production.
- **Secrets.** Claim codes are 72-bit and stored as hashes. Passwords and PINs use salted PBKDF2. Backups exclude every hash. No secrets are in the repository or the archive; the archive has deployment IDs only.
- **Migrations** are additive, recorded in `__app_migrations`, and every request checks readiness before serving.
- **Invite email** signs in before rotating links, compare-and-swaps each link, never returns a link in the response, and skips reserved test domains.
- **The chat write path** re-checks room status, membership, role, and alive status in the insert itself.
